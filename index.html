HANDBOOK SECTION 06

What the system is

SAHAAY is a role-based food-surplus redistribution application. Its active client is a Flutter app (sahaay/lib/main.dart and supporting service/widgets). The app authenticates users with Firebase, sends Firebase ID tokens to a FastAPI application (sahaay_backend/), and the backend uses its server-side Supabase service-role client to read and persist application data. A second FastAPI process (sahaay-ai-service/) provides surplus prediction, weighted NGO ranking, escalation calculations, reliability calculations, food-safety rules, and PDF generation. The backend calls it over HTTP through AIClient; the Flutter app does not directly invoke that service.

The source contains three different kinds of “AI” behavior:

  • A trained tabular regressor for predicted surplus: a scikit-learn RandomForestRegressor trained from a small checked-in sample CSV. It is not evidence of a validated production model.
  • A deterministic weighted matching heuristic with OSRM road distance when available and haversine fallback. It is not a trained ranking model.
  • Rule/formula features for food safety, restaurant reliability, and escalation. These are conventional rules/calculations, not learned models.

    • See the AI deep dive for formulas, execution order, failure behavior, tests, and limitations.

    Important implementation reality checks

  • The AI service is a real separate HTTP dependency, not just a package imported into the backend. sahaay_backend/app/services/ai_client.py calls its versioned endpoints.
  • The main backend’s NGO matching path is stricter than the isolated AI ranker: it requires real coordinates, valid hours, positive weight capacity, explicit food-category and dietary preferences, compatible category/diet, and a convertible kg/g donation quantity before making a ranking request.
  • servings are not convertible to kilograms. The backend returns an explicit insufficient-data result instead of fabricating weight.
  • The last local matching-readiness migration (20261017040000_profile_complete_ngo_matching.sql) defines readiness from profile completeness and deliberately does not inspect verified or demo_verified. Earlier migrations did use verification flags. This is a material policy decision to confirm against the product’s intended eligibility rule; the live function body was not inspected.
  • The initial schema snapshot contains 12 broad anon policies on identity/profile tables. Later local migrations remove these and add a fail-closed check that also considers PUBLIC; local static tests assert this history. Whether those migrations were applied to the configured live database is UNKNOWN.
  • The release-site CTA and page are committed in the recovery branch, but no production website is shown as deployed. The direct APK Release asset exists; the website source itself is not a live-hosting proof.

    HANDBOOK SECTION 21

    Trust and data ownership

  • Firebase Authentication establishes the principal. The backend derives the Firebase UID from a verified ID token; it does not accept a client-supplied UID as an identity assertion (sahaay_backend/app/dependencies.py:12-39).
  • The backend maps firebase_uid to users and joined role profiles. The backend’s service-role key bypasses RLS, so API route role and ownership checks are security-critical (app/supabase_client.py:9-15, app/dependencies.py:24-66).
  • Supabase rows are authoritative for users, providers, NGOs, volunteers, donations, claims, deliveries, offers, and persisted notifications.
  • The AI service receives backend-built input DTOs and returns calculations. Its output is not authoritative for recipient identity or persisted offer transitions: the backend filters ranking IDs against its eligible candidate set and persists candidates/offers through the database workflow (app/routers/ai_features.py:788-891, app/services/donation_offers.py).
  • FCM acceptance means the provider accepted a send request, not that a device received or displayed it.
    • HANDBOOK SECTION 22

    Synchronous and asynchronous behavior

  • Flutter request/response operations are synchronous HTTP workflows from the user’s perspective.
  • The backend calls the AI service synchronously through httpx.Client, with general and matching-specific timeouts; the client maps transport errors to a controlled unavailable exception. It does not configure retries (ai_client.py).
  • Backend notification creation persists first, then attempts FCM. Push failure does not roll back the database row.
  • Ranked offers are persisted and advanced through database RPC functions. Two in-process backend schedulers poll for escalation/expiry work during FastAPI lifespan. The backend Dockerfile runs one Uvicorn worker; README advises one backend replica until scheduler leadership is externalized.
  • The AI service’s own escalation endpoint is a stateless calculation; the backend’s durable timed offer sequence is a separate implementation.

  • sell_through_ratio
  • food_category_enc
  • day_of_week_enc
  • day_of_month

The checked-in sample CSV has only 30 rows. The reported code path contains a metric computation; no measured MAE from an audit run is claimed here.

    Inference sequence

  • FastAPI/Pydantic parses SurplusPredictionRequest.
  • Router calls predict_surplus.
  • _load calls _ensure_model_trained; if either model or encoder file is absent, it imports and executes train(), then joblib-loads both (prediction.py:21-34).
  • Category and weekday are label-encoded. If unseen, _safe_encode returns class index 0 rather than failing (prediction.py:37-46). Although the helper comment says the router can tell the user in note, the router does not set a fallback-specific note.
  • The seven numeric features above are assembled into a one-row pandas frame.
  • Model prediction is clipped to [0, food_prepared_kg], converted to float, and rounded to two decimals (prediction.py:49-80).
  • If surplus is at most 2 kg, recommended preparation equals current prepared amount. Otherwise it reduces preparation by 70% of predicted surplus, rounds to 2 decimals and clamps at zero (prediction.py:83-116).
  • Router returns the predicted number, recommendation, recommended preparation, input echo, and defaults.

    • Actual model type: scikit-learn Random Forest regression over tabular data. No neural network, embeddings, vector database, LLM/external AI API, online learning, model registry, or production-trained data pipeline was found. Category/day integer encodings impose arbitrary ordinal numbers on categorical classes; a tree can split these numeric codes, but the values are not semantic distances. No model calibration or measured generalization evidence is present.

    HANDBOOK SECTION 46

    Matching/ranking: exact algorithm

    The main backend constructs a trusted candidate set; the AI service scores each candidate. The isolated service itself does not query organizations or check profile status.

    Distance

  • If USE_ROAD_DISTANCE=True (default), build an OSRM route/v1/driving/{lon1},{lat1};{lon2},{lat2} request with overview=false, request timeout 3 seconds by default, require HTTP success and code == "Ok" plus a route, then use first-route meters / 1000 rounded to two decimals (matching.py:47-67).
  • Any routing exception is swallowed by get_distance_km; fallback is Haversine straight-line distance with Earth radius 6371 km, rounded to two decimals (matching.py:32-45,69-82).
  • Score is 0 at or beyond 15 km; inside the limit: D = round((1 - distance_km / 15) × 100, 2) (matching.py:85-89).

    • Quantity fit

    Let donation quantity be q, NGO minimum m, and maximum M:

    $$

    Q(q,m,M) =

    \begin{cases}

    100 \cdot \max(0, M/q), & q > M \\

    70 \cdot \max(0, q/m), & q < m \text{ and } m > 0 \\

    100, & q < m \text{ and } m = 0 \\

    \min(100, 60 + 40q/M), & m \le q \le M

    \end{cases}

    $$

    Each result is rounded to two decimals (matching.py:92-107). Main backend passes min_capacity_kg = 0.0, so only too-large vs within-capacity branches normally apply. Backend also hard-excludes quantity_kg > capacity_kg; the AI ranker’s oversized score branch is therefore not normally reached for backend-generated candidates.

    Dietary, pickup window, reliability and total

  • Dietary score T is 100 if donation type is included in NGO accepted types or NGO accepts "any"; otherwise 0 (matching.py:110-114).
  • Time score P is 100 when pickup time is inside the inclusive NGO window, otherwise 0. Windows crossing midnight use (pickup >= start) OR (pickup <= end). Malformed time strings score 0 (matching.py:116-130).
  • Reliability component R is the donation’s restaurant_reliability_score, passed identically for every NGO in a request.
  • Final score:

    • $$

    S = 0.30D + 0.25Q + 0.20T + 0.15P + 0.10R

    $$

    It is rounded to two decimals; rows sort by descending final_score, and one-based ranks are assigned afterward (matching.py:133-185). Python’s stable list sort preserves incoming candidate order for ties; no explicit secondary tie-break is coded.

    Interpretation: it is a heuristic score, not a probability. NGOInput accepts reliability_score, but the calculation does not use it. The restaurant reliability term is constant across all candidates and therefore changes absolute score but not relative NGO order.

    Main backend candidate gate / post-ranking

    sahaay_backend/app/routers/ai_features.py is the trusted integration layer:

  • POST /api/v1/donations/{id}/match requires provider role and confirms donation ownership.
  • Only available, unexpired donations are matched. Provider coordinates fall back to donation coordinates; invalid/out-of-range coordinates produce insufficient_data.
  • Pickup deadline is converted into Asia/Kolkata local HH:MM; unusable deadline, quantity, or dietary value returns insufficient_data.

  • Candidate NGO rows and corresponding user rows are loaded. Incomplete profile, invalid/missing location/hours/capacity, missing category/diet preferences are excluded.     HANDBOOK SECTION 48

    Reliability score

    For offered count O, completed C, accepted A, cancelled X, and average rating r on 0–5:

    $$

    \text{score} =

    40(C/O) + 30(r/5) + 20(1-X/O) + 10(A/O)

    $$

    Each ratio returns zero when O <= 0; result is rounded and clamped to 0–100 (core/reliability.py:18-68, weights in config.py:74-79). Grades: Excellent ≥85, Good ≥70, Average ≥50, Below Average ≥30, otherwise Poor. Router rejects completed > offered, but does not similarly require accepted or cancellations ≤ offered; final clamping masks some inconsistent inputs. With zero offers and rating zero, the cancellation contribution remains 20.

    Matching is a two-layer design:

    Backend eligibility and normalization

    Donation gates

  • Caller must be provider and donation owner; donation must remain available and unexpired.
  • Provider coordinates may fall back to donation coordinates. Coordinates must be valid latitude/longitude ranges; missing/malformed matching inputs produce an explicit insufficient-data outcome.

  • Quantity is normalized to kg only for recognized kg/g spellings with SI conversion. Servings are deliberately not interpreted as kg.
  • Category is normalized through food_mapping.map_food_category; unknown category is rejected explicitly instead of being assigned to an unrelated category.
  • Dietary field must be recognized/usable. The backend treats dietary preferences separately from preferred food categories.

    • NGO candidate gates

    The backend loads NGO rows and joins each to its user/profile data. Matching requires essential values such as:

  • non-empty organization/profile fields required by ngo_profile_is_complete;
  • valid latitude and longitude;
  • non-empty usable operating-hours range;
  • positive maximum capacity in kg;
  • configured preferred food types and dietary preferences;
  • category compatibility, food dietary compatibility, pickup time, and capacity;
  • accepted logistics/vehicle state as a separate availability/order attribute.

    • Missing required fields exclude an NGO; they do not receive a favorable zero/default score. Backend may retain candidates where volunteer logistics is needed, but marks that requirement and orders after the vehicle-capable tier.

    HANDBOOK SECTION 57

    Food category mapping

    Flutter categories include cooked, bakery, dairy, packaged, raw, and Other. The main backend’s category mapping is deliberate; Other is retained as other for the AI service’s supported enum rather than guessed as cooked/dairy. Category compatibility checks accepted NGO preferred food types; no match is excluded before rank scoring. See sahaay_backend/app/services/food_mapping.py and tests for mapping coverage.

    The AI schema supports FoodCategory values cooked, bakery, dairy, packaged, raw, other. Safety rules have a default threshold for other. This avoids a schema validation failure for the Flutter option and avoids silently misclassification.

    HANDBOOK SECTION 58

    Dietary semantics

    Preferred food types and dietary preferences are distinct profile data:

  • Preferred food types describe what categories the NGO wants to receive.
  • Dietary preferences describe food suitability (for example dietary types).

    • The backend performs compatibility gating on dietary preferences. A mismatch is not converted into “low preference” unless the compatibility policy explicitly allows the case; the AI score’s dietary term is an input to ranking, not the security or eligibility decision.

    The AI ranker itself gives dietary score 100 when the donation dietary_type appears in NGO accepted_dietary_types or the NGO accepts "any"; otherwise 0. This same scoring semantics is not sufficient to describe every richer backend compatibility rule—backend filters remain authoritative.

    HANDBOOK SECTION 59

    Distance and quantity

    AI service attempts OSRM driving distance with a configured timeout, then falls back to haversine distance. Within the 15 km score range:

    distance_score = (1 - distance_km / 15) * 100; 15 km or farther scores zero.

    Quantity fit is capacity-aware; backend first excludes capacity violations. It passes minimum capacity as zero in the common path, so ranker normally uses the under-capacity formula min(100, 60 + 40 × quantity/max_capacity). See AI algorithm detail.

    HANDBOOK SECTION 60

    Ranked offers are not just a sort

    POST /api/v1/donations/{id}/match calculates a ranking and stores candidate/offer state. The offer sequence is persisted independently and issues one five-minute offer at a time. The scheduler/manual escalation RPC advances a due offer using database time and row locks. Acceptance creates/accepts the claim atomically. See ranked-offer workflow.

    Ranked NGO Offers and Escalation Workflow

    HANDBOOK SECTION 65

    What persists and what does not

    The AI service’s /escalation/check is a stateless formula endpoint. It receives rank IDs, index, state, and timestamps; it does not persist offers, locks, claim state, or notifications. The real workflow is the main backend plus PostgreSQL migrations/RPCs:

  • donation_match_candidates: durable candidate order and component details.
  • donation_offers: durable offer status and deadline.
  • Database RPCs: atomic start, respond/advance, expire due.
  • Backend scheduler: polls due offers and invokes database expiry RPC.

    • Do not describe the stateless AI escalation endpoint as the production offer engine.

    HANDBOOK SECTION 66

    End-to-end lifecycle

  • Candidate refresh: provider owns an available, unexpired donation; backend validates it and asks AI to rank eligible candidates. Returned NGO IDs are checked against the backend’s set.
  • Persist and start: backend calls start_donation_offer_sequence(donation_id, candidates). SQL locks donation, rejects closed/expired state, returns current pending/already-started state when applicable, persists validated candidates, and starts the highest-ranked still-eligible NGO.
  • Single pending offer: a partial unique index enforces at most one pending offer per donation. Default offer window is five minutes from database clock_timestamp().
  • NGO response: NGO lists only its offers and responds via respond_to_donation_offer(offer_id, ngo_id, decision). SQL checks ownership, pending status, donation state, deadline, and serializes on donation then offer lock.
  • Accept: atomically changes donation to claimed, inserts/accepts claim, marks offer accepted, and returns other pending claims for backend reconciliation/notifications.
  • Decline/timeout: marks current offer; selects next unoffered candidate in persisted rank order, subject to current NGO eligibility, and creates the next pending five-minute offer.
  • Exhaustion: if no further candidate exists, returns exhausted state; backend can notify provider that all offers are exhausted.
  • Scheduler/manual path: bounded scheduler calls expire_due_donation_offers; provider manual escalation endpoint uses the same database-clock transition. Before deadline it returns not due without changing state.

    RLS and access design

    The initial schema enables RLS on core tables yet also gives anon broad grants and policies on sensitive identity profiles. This combination is a serious design hazard if left effective. The local 20261003000000_fix_anon_rls_policies.sql removes 12 broad policies; 20261015000000_harden_anonymous_policy_check.sql additionally handles policies targeting PUBLIC/multi-role combinations on sensitive tables and fails closed when it detects broad true predicates. The intended application trust path is Flutter → Firebase ID token → FastAPI → Supabase service role; Flutter business operations should not rely on unrestricted anonymous table access.

    Important caveats:

  • The migrations’ comments describe intended public read policies for available donations and verified provider/NGO profiles; verify current policy text and whether those reads are truly required.
  • Service-role access bypasses RLS, making backend role/ownership checks part of the security boundary.
  • REVOKE statements on offer tables/RPCs and service-role-only grants are intentional.
  • No live pg_policies, grants, pg_class.relrowsecurity, pg_proc, pg_trigger, or indexes were inspected. Effective RLS is UNKNOWN.

    HANDBOOK SECTION 122

    Architecture and authentication

    1. What is SAHAAY’s architecture?

    Flutter is the client. Firebase Authentication establishes the user identity. The main FastAPI backend verifies Firebase ID tokens, maps the UID to a role profile, and uses a server-side Supabase service-role client. A separate FastAPI AI service handles prediction and calculations. The backend, not Flutter, connects the AI service.

    2. Why is there a separate backend if Flutter can connect to Supabase?

    The backend centralizes authorization and business rules. It verifies Firebase tokens, derives the user ID and role, checks ownership, and protects service-role credentials. Supabase service-role bypasses RLS, so those API checks are security-critical.

    3. How does a Firebase user become a SAHAAY user?

    Firebase sign-in gives the client an ID token. The backend verifies it, extracts the UID, looks up users.firebase_uid, and returns the persisted role profile. A new Firebase identity must complete backend profile enrollment; the client cannot declare its own trusted role.

    4. Is the Supabase anon key a secret?

    No. If embedded in a client, it is public. The security boundary must be RLS/grants and the authenticated backend flow. The service-role key is secret and must stay server-side.

    5. Does the backend trust a client-supplied UID?

    No. It uses the UID from verified Firebase token claims, then maps it to the application user row.

    6. Does successful Firebase login prove the account has an app profile?

    No. Firebase authentication and SAHAAY profile enrollment are separate. The backend may return missing-profile behavior or allow a supported profile-adoption flow.

    HANDBOOK SECTION 123

    AI and prediction

    7. What machine-learning model does the project use?

    The surplus prediction service uses scikit-learn RandomForestRegressor with 200 trees and max depth 6. It is trained on seven tabular features. Other AI-labelled features are not trained ML models.

    8. What data was used to train it?

    The checked-in sample CSV has 30 rows. The training code uses a seeded 80/20 split and prints a holdout MAE. No measured MAE value or production dataset provenance is asserted by this audit.

    9. What are the predictor’s seven features?

    Prepared kg, sold kg, sell-through ratio, encoded food category, encoded weekday, day of month, and month.

    10. How does prediction avoid impossible surplus values?

    It clamps predicted surplus between zero and prepared quantity, then rounds. Recommendation logic either retains the prepared amount for very small predicted surplus or subtracts 70% of predicted surplus and clamps at zero.

    11. Is NGO matching a trained AI model?

    No. It is a deterministic weighted score: 30% distance, 25% quantity fit, 20% dietary compatibility, 15% pickup-time fit, and 10% provider reliability.

    12. How is distance calculated?

    The AI service attempts OSRM driving distance with a short timeout. If route lookup fails, it falls back to haversine straight-line distance. The fallback is not a road-distance estimate.

    13. Is a match score an acceptance probability?

    No. It is a heuristic score from 0 to 100. No calibration or probability validation is present.

    14. How does the AI service handle unseen food categories?

    Prediction label encoding falls back to encoded class zero. In matching, the schema has explicit other; backend category mapping should deliberately map Flutter’s Other option to it instead of an unrelated category.

    15. What is the purpose of the backend matching layer?

    It loads trusted database rows, checks ownership and donation state, filters NGOs with incomplete or incompatible profiles, maps units and categories, calls the ranker, validates returned IDs, applies vehicle logistics order, and persists the candidate/offer workflow.

    16. Why are servings not converted to kg?

    Servings are counts, not a mass unit. Converting them to kg without a measured conversion would fabricate capacity eligibility. The matching path requires a recognized kg/g quantity.

    HANDBOOK SECTION 124

    Matching, offers, and delivery

    17. How are NGO candidates made eligible?

    Backend checks required location, hours, positive max capacity, food categories, dietary preferences, quantity conversion, pickup time, and compatibility. Missing essential data means exclusion rather than defaulting to eligible.

    18. Are preferred food types and dietary preferences the same field?

    No. Preferred food types describe categories an NGO wants; dietary preferences describe what kinds of food are suitable. The profile stores them separately.

    19. What does vehicle-aware matching do?

    It applies a logistics-aware ordering/flag after AI score ranking without altering the score. It distinguishes available transport from unknown/unavailable and may indicate volunteer delivery requirement.

    20. Does the AI escalation endpoint manage the actual offer queue?

    No. It is stateless. The actual workflow is stored in Postgres candidate/offer tables and advanced by database RPCs.

    21. How many NGOs are offered a donation simultaneously?

    At most one pending offer per donation; a partial unique index enforces this in the local migration design.

    22. Who decides whether an offer has expired?

    The database clock in the offer RPCs is authoritative. The scheduler/manual provider check calls the same transition path; client clocks are not trusted.

    23. What happens when an NGO declines or times out?

    The current offer is marked declined/timed out, and the next ranked, eligible, not-yet-offered NGO receives a new five-minute pending offer. If none remain, the sequence is exhausted.

    24. How does acceptance avoid two NGOs claiming at once?

    The offer RPC locks the donation, conditionally changes it from available, and performs offer/claim changes in one transaction. Other pending claims/offers are reconciled as part of the transition.

    25. When is a volunteer requested?

    Only after both provider and NGO decline transport and a participant explicitly requests a volunteer. The database creates or safely reuses an unassigned task; the volunteer assignment RPC guards the transition.

    26. Does accepted offer mean food was handed over?

    No. Acceptance creates the claim. Physical handover uses a separate expiring verification code, hash storage, attempt limit, and atomic handover-completion RPC.

    27. What is the effect of handover verification?

    It marks claim/donation completion and stores the verification timestamp; backend then attempts receipt generation and notifications. Delivery/impact triggers may also record impact when delivery reaches delivered state.

    HANDBOOK SECTION 125

    Database and security

    28. Why are database migrations important to matching?

    The matching and offer workflow relies on profile columns, candidate/offer tables, constraints, indexes, and SQL RPCs. Local Python code alone cannot create or guarantee those objects.

    29. Were the migrations verified against production?

    No. Only local SQL was inspected. The configured Supabase project, migration history, live schema and effective policies were not queried.

    30. What was wrong with the initial RLS policies?

    The base schema included broad anonymous insert/select/update policies on identity/profile tables. Later local migrations drop them and add a broad-policy check, including PUBLIC. Whether the fix was applied remotely is unknown.

    31. Why is service-role use sensitive?

    Service role bypasses RLS. If a route misses ownership/role authorization, the database will not provide the intended row isolation on its behalf.

    32. Is the AI service protected by application authentication?

    No authentication middleware was found. Its integration documentation expects private/internal network access. The actual deployment network boundary was not verified.

    33. Is the NGO verification endpoint available?

    A module defines it, but the main app does not mount that router in this revision, so the endpoint is unreachable through the configured FastAPI app.

    34. Is FCM push reliable delivery?

    No. The backend persists the notification row, then attempts FCM. A successful send API response does not prove display; push failure does not roll back business state.
